Kairo

State-based process monitoring and concept-drift detection for event logs — with textual abstractions and LLM access built in.

What it does

Kairo describes the behaviour of a process through three complementary notions of state computed from a traditional event log, follows how state occupancy evolves over calendar windows, and turns significant changes in those signals into concept-drift indicators. Every computed object has an abstract_* twin that renders it as text, so a language model — hosted or local — can read a full analysis and reason about it.

Concepts

Intra-case, resource, and inter-case states; how clustering turns features into states.

Abstractions

Every object as prompt-ready text: states, transitions, distributions, signals.

LLM

Connectors for Anthropic, OpenAI, Google, and local servers; knowledge injection; plot explanation.

Installation

Editable install inside the thesis workspace, or standalone.

Kairo lives in the thesis repository and is wired into the uv workspace as an editable dependency — uv sync at the repository root installs it. Standalone:

pip install -e kairo            # from the thesis root
pip install -e "kairo[vision]"  # + kaleido, for explain_plot / save_figure

Quick start

Log in, states out, question answered.

import kairo

log = kairo.read_log("log.xes")
log = kairo.map_columns(log, {
    "case ID": "case:concept:name", "activity": "concept:name",
    "timestamp": "time:timestamp", "resource": "org:resource", "event duration": None,
})

result = kairo.run_intra_case(log, kairo.IntraConfig(
    clustering="som", grid=(3, 3), pca_components=4, window_minutes=1440,
))

kairo.plot_state_grid(result.states).show()
kairo.plot_drift_signal(result.signal).show()

print(kairo.abstract_result(result))          # the whole run as text

answer = kairo.llm.ask(
    "Where does the process drift, and what characterises the change?",
    result=result, log=log,
    executor=kairo.llm.anthropic_query,       # or openai_query / google_query / local_query
)

The same analysis can be driven step by step — see Step API — and the demo notebook notebooks/kairo_demo.ipynb walks every layer.

Concepts

Three notions of state, one pipeline shape.

The three perspectives

PerspectiveOne sample =Features describe
Intra-caseone event the event's case prefix: activity frequencies, directly-follows counts, vocabulary, progress, current and past activities.
Resourceone calendar window of W minutes the resource pool in that window: events and active cases per resource, mean durations, cross-resource waits, activity-resource shares, handover shares.
Inter-caseone calendar window of W minutes the whole system: active cases, arrivals, completions, events per case, within-case pacing (mean/std Δt), stalled cases, case-attribute mixes.

From features to states

Feature vectors are optionally compressed with PCA (elbow rule by default) and optionally standardized, then clustered: a SOM lays states out on a grid, k-means produces k states, DBSCAN produces density clusters plus a Noise state. A state is a region of similar behaviour; each sample is assigned one, giving state trajectories over time.

From states to drift

Intra-case: per-window state distributions are compared against a reference (previous window, rolling mean, or full-log baseline) under a divergence (KL, Jensen–Shannon, total variation, Hellinger). Resource and inter-case: each window's compressed vector is compared with the previous window's under a vector distance. Spikes in either signal are drift candidates — the transitions table and state profiles then explain what changed.

Pipelines

One frozen config per perspective; one result shape.

Configs

kairo.IntraConfig(
    features=("activity_freq", "bigram", "vocab", "progress", "current", "history"),
    history=3,
    skip_pca=False, pca_components=None, scaling="none",
    clustering="som", metric="euclidean",
    grid=(3, 3), som_init="random",        # SOM
    n_clusters=6,                          # k-means
    eps=0.5, min_samples=5,                # DBSCAN
    window_minutes=60,
    divergence="js", reference="previous", lookback=5,
    seed=7,
)
kairo.ResourceConfig(..., resources=(), activities=(), signal_metric="euclidean")
kairo.InterConfig(..., stall_minutes=60, numeric_attrs=(), categorical_attrs=())

pca_components=None selects the elbow rule; empty tuples mean "all". Configs are frozen dataclasses: JSON-serializable, hashable, reproducible.

Runners

result = kairo.run_intra_case(log, config)   # -> StateResult
result = kairo.run_resource(log, config)
result = kairo.run_inter_case(log, config)
result = kairo.run(log, "intra_case")        # default config

StateResult

FieldContent

result.to_dict() gives a light JSON summary; abstract_result(result) the full textual account.

Step API

The runners are thin — every step is public and composable.

Features

fs = kairo.build_features(log, "intra_case", features=("activity_freq", "progress"), history=3)
fs = kairo.build_features(log, "resource", window_minutes=60, resources=("r1", "r2"))
fs = kairo.build_features(log, "inter_case", window_minutes=60, stall_minutes=60,
                          numeric_attrs=("amount",), categorical_attrs=("region",))

Only the requested features are computed — each is its own function inside kairo.features.intra / resource / inter. The returned FeatureSet carries matrix, index, groups (feature key → columns), meta, and values(). Share features keep log-wide denominators even when a resource filter narrows the produced columns.

Reduce · cluster · states · drift

reduced, pca = kairo.reduce(fs.values(), skip_pca=False, n_components=None, scaling="none")

model = kairo.cluster_som(reduced, grid=(3, 3), metric="euclidean", init="random", seed=7)
model = kairo.cluster_kmeans(reduced, n_clusters=6, metric="cosine")
model = kairo.cluster_dbscan(reduced, eps=0.5, min_samples=5)

assigned    = kairo.assign_states(fs, model)
transitions = kairo.case_transitions(fs, model)          # intra: within-case
profiles    = kairo.state_profiles(fs, model)            # what characterises each state
matrix      = kairo.transition_matrix(model.state_ids, model.n_states, model.labels)

dist   = kairo.state_distribution(fs.index["time:timestamp"], model.state_ids,
                                  model.n_states, window_minutes=1440)
signal = kairo.drift_signal(dist, divergence_kind="js", reference="previous", lookback=5)
shift  = kairo.window_vector_shift(fs.index["window_start"], reduced, metric="euclidean")

Diagnostics

kairo.k_distances(reduced, k=5)        # DBSCAN eps candidate (knee)
kairo.state_distances(model)           # pairwise state-vector distances
kairo.silhouette(reduced, model)       # assignment quality
kairo.top_drift_windows(signal, k=5)   # strongest windows

Abstractions

Everything the pipeline computes, as prompt-ready text.

Same contract as pm4py's abstractions: plain string in, no network, truncated to max_len characters, optional include_header.

LLM

Connectors, knowledge injection, and analysis prompting.

Connectors

kairo.llm.anthropic_query("prompt", model="claude-opus-5")
kairo.llm.openai_query("prompt", model="gpt-5")
kairo.llm.google_query("prompt", model="gemini-2.5-flash")
kairo.llm.local_query("prompt")                 # LM Studio / Ollama; model auto-discovered
kairo.llm.query("prompt", provider="local")     # dispatch by name or KAIRO_LLM_PROVIDER
kairo.llm.available_models("local")             # what the local server has loaded

Shared keywords: model, api_key, api_url, system, max_tokens, image_path, extra_payload, timeout. Keys come from the environment at call time (KAIRO_* first). Every higher-level function takes an executor — any callable (prompt, **kwargs) → str — so custom backends plug in without touching kairo.

Knowledge injection

Hardcoded blocks in kairo.llm.knowledge: drift_detection (the research framing), process_mining (terminology and drift types), method (the kairo pipeline and its parameters), statistics (how to read the diagnostics) — plus log, derived from the current log.

kairo.llm.inject(log=log, parts=("method", "log"), max_len=4000)

Prompting

prompt = kairo.llm.build_prompt(question, result=result, log=log)   # no network

answer = kairo.llm.ask(question, result=result, log=log,
                       executor=kairo.llm.local_query)

reading = kairo.llm.explain_plot(fig, "Where would you place the drift?",
                                 result=result, executor=kairo.llm.anthropic_query)

explain_plot renders the figure to PNG (kaleido) and sends it to a vision-capable model. Prompts are assembled as <knowledge>, <analysis>, <question> blocks, each under its own share of max_len.

Natural language → config

cfg = kairo.llm.nlp_to_config(
    "weekly windows, DBSCAN with a tight eps, cosine distance",
    perspective="intra_case", executor=kairo.llm.anthropic_query,
)
kairo.run_intra_case(log, cfg)

The model fills a JSON object against the config's schema; kairo validates and instantiates the dataclass. With obtain_config=False the prompt is returned instead — the seam for agentic loops that propose, run, read abstract_result, and propose again.
