Kairo

State-based process monitoring and concept-drift detection for event logs — with textual abstractions and LLM access built in.

Package structure

What it does

Kairo describes a process through three complementary notions of state computed from a traditional event log, follows how state occupancy evolves over calendar windows, and turns significant changes in those signals into concept-drift indicators. Every computed object has an abstract_* twin that renders it as text, so a language model — hosted or local — can read a whole analysis and reason about it.

The three perspectives

PerspectiveOne sample isFeatures describe
Intra-caseone event that event's case prefix — activity frequencies, directly-follows counts, vocabulary, progress, current and past activities.
Resourceone calendar window the resource pool — events and active cases per resource, mean durations, cross-resource waits, activity-resource shares, handover shares.
Inter-caseone calendar window the whole system — active cases, arrivals, completions, events per case, within-case pacing, stalled cases, case-attribute mixes.

How a run works

All three perspectives share one pipeline shape. Feature vectors are optionally compressed with PCA and optionally standardized, then clustered — a SOM lays states on a grid, k-means gives k states, DBSCAN gives density clusters plus a noise state. Each sample is assigned a state, producing state trajectories over time. Intra-case then compares per-window state distributions against a reference under a divergence; the two windowed perspectives compare each window's compressed vector with the previous one's. Spikes are drift candidates — the transitions table and state profiles explain what changed.

Read the whole surface on the API page.

Installation

Kairo ships inside the thesis repository.

It is wired into the uv workspace as an editable dependency, so one command from the repository root installs it along with everything else:

uv sync

That is all. import kairo then works in the notebooks, the dashboard, and any script run with uv run.

API keys

Connectors read keys from the environment at call time — never at import — checking the KAIRO_* name first and the provider's usual one second. Put them in a .env at the repository root:

KAIRO_ANTHROPIC_API_KEY  or  ANTHROPIC_API_KEY
KAIRO_OPENAI_API_KEY     or  OPENAI_API_KEY
KAIRO_GOOGLE_API_KEY     or  GOOGLE_API_KEY
KAIRO_LOCAL_API_URL      (default http://localhost:1234/v1)
KAIRO_LLM_PROVIDER       (default provider for kairo.query)

Local servers such as LM Studio and Ollama need no key. In a notebook, load the file before importing anything that reads it: from dotenv import load_dotenv; load_dotenv(). With uv run --env-file .env … the variables are set before Python starts.

Quick start

Log in, states out, question answered.

Run a pipeline

import kairo

log = kairo.read_log("log.xes")
log = kairo.map_columns(log, {
    "case ID": "case:concept:name", "activity": "concept:name",
    "timestamp": "time:timestamp", "resource": "org:resource", "event duration": None,
})

result = kairo.run_intra_case(log, kairo.IntraConfig(
    clustering="som", grid=(3, 3), pca_components=4, window_minutes=1440,
))

kairo.plot_state_grid(result.states).show()
kairo.plot_drift_signal(result.signal).show()

Or drive the steps yourself

fs = kairo.build_features(log, "inter_case", window_minutes=1440)
reduced, pca = kairo.reduce(fs.values(), n_components=3, scaling="standardize")
model = kairo.cluster_kmeans(reduced, n_clusters=4)
shift = kairo.window_vector_shift(fs.index["window_start"], reduced)

Turn it into text

print(kairo.abstract_result(result))        # the whole run
print(kairo.abstract_states(result.states)) # just the states

Ask a model

answer = kairo.ask(
    "Where does the process drift, and what characterises the change?",
    result=result, log=log,
    executor=kairo.anthropic_query,   # or openai_query / google_query / local_query
)

prompt = kairo.build_prompt("Where is the drift?", result=result, log=log)  # no network call

The demo notebook notebooks/kairo_demo.ipynb walks every layer, including a local model through LM Studio. The dashboard runs on the same functions: streamlit run dashboard/app.py.

Package structure

Six subpackages behind one flat public surface.

Everything on the API page is callable as kairo.name. The subpackages hold the implementation and stay importable for anything the flat surface does not expose.

kairo/
  __init__.py          the flat public API
  data/                the event log itself
    schema.py          canonical columns, roles, feature catalog
    log.py             read XES/CSV, map columns, statistics
    windows.py         calendar-window helpers
  features/            feature extraction, one function per feature
    intra.py           per-event prefix features
    resource.py        per-window resource features
    inter.py           per-window system and attribute features
  analysis/            the analytical steps
    reduce.py          standardization, PCA
    cluster.py         SOM / k-means / DBSCAN -> StateModel
    states.py          trajectories, transitions, distributions, profiles
    drift.py           divergences, references, drift signals
  pipeline/            end-to-end runs
    config.py          IntraConfig, ResourceConfig, InterConfig
    run.py             the runners and StateResult
  viz/                 figures
    palette.py         state colours, shared across every plot
    plots.py           every plotly figure
  llm/                 text and language models
    abstract.py        every object -> text
    connectors.py      anthropic / openai / google / local
    knowledge.py       hardcoded domain knowledge + injection
    prompt.py          build_prompt, ask, explain_plot, nlp_to_config
SubpackageHoldsDepends on
kairo.dataReading, mapping, and describing an event log.—
kairo.featuresThe three feature builders and FeatureSet.data
kairo.analysisReduce, cluster, states over time, drift signals.data, features
kairo.pipelineConfigs, runners, StateResult.data, features, analysis
kairo.vizPalette and every figure.data, analysis
kairo.llmAbstractions, connectors, knowledge, prompting.all of the above

Dependencies point one way only, so there are no import cycles. Functions are pure: no global state, no caching, no I/O beyond reading the log file you name. The Streamlit dashboard consumes this API and adds only widgets and its own caching layer.

result.to_dict() gives a JSON-ready summary without the matrices. The three nested objects carry what the plot and abstraction functions read:

ObjectAttributes
